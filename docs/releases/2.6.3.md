# LLM Monitor 2.6.3

[English](#english) · [简体中文](#简体中文)

## English

### Fixed

- **Antigravity / agy TTFT & streaming decode speed resolved (Option B).**
  - Clarified why `f1.f12` earlier appeared negligible (0.01–0.18s): in ~85% of Antigravity turns involving tool calls (`step_payload.f20.f7` present) or non-streaming short responses, payloads are delivered in single batch packets rather than streaming decode.
  - For **pure streaming text responses** (`!isToolCall && f12 >= 0.5s`), `f1.f11` represents true TTFT (median ~3.0s–4.6s, covering prefill and reasoning), while `f1.f12` represents the actual streaming duration (median ~3.8s, yielding a realistic ~294 tok/s decode throughput).
  - Adopted Option B: `TTFT = f1.f11` is recorded across calls. For pure streaming text responses, `durationSeconds` supplies `ttftSeconds + streamingSeconds` so the decoding duration denominator `duration - ttft` cleanly evaluates to `f12`. For tool calls or non-streaming short responses, `durationSeconds = nil` is assigned to prevent near-zero division spikes.
  - Bumped cache indexes: Antigravity v11 → v12, agy v6 → v7 to rebuild clean metrics.

## 简体中文

### 修复

- **Antigravity / agy 首字延迟（TTFT）与流式解码速度度量落地（方案 B）。**
  - 排查厘清了此前 `f1.f12` 仅 0.01~0.18s 的根本原因：在占 ~85% 的工具调用（`step_payload.f20.f7` 存在）或非流式短响应场景中，服务端整包批量下发，并不发生流式逐字解码。
  - 针对**纯文本流式输出**（`!isToolCall && f12 >= 0.5s`），`f1.f11` 是模型真实首字耗时（TTFT，P50 ~3.0s-4.6s，覆盖 prefill 与内部思考），`f1.f12` 是真实流式解码时长（中位数 ~3.8s，对应 ~294 tok/s 硬件物理吞吐）。
  - 全面落地方案 B：全量调用采集 `f1.f11` 作为 TTFT；纯文本流式调用供给 `(ttft ?? 0) + streamingSeconds` 作为 `durationSeconds`，使得解码分母 `duration - ttft` 精确等于流式耗时 `f12`；工具调用及非流式短响应（`f12 < 0.5s`）时长设为 `nil`，既保留 TTFT 又彻底消除除零速度尖峰。
  - 缓存索引版本递增：Antigravity v11 → v12，agy v6 → v7，全量重置重建纯净指标。
